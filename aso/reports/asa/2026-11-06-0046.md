## NEW FINDING: the guard cannot see installs — and would negate its own winners

`aso/asa_guard.py` reads two metric keys that Apple's v5 reporting API never returns:

| guard reads (line) | Apple actually returns |
|---|---|
| `_m(m,'installs')` — lines 148, 157, 169 | `totalInstalls` / `tapInstalls` |
| `_m(m,'conversionRate')` — line 158 | `totalInstallRate` / `tapInstallRate` |

`_m()` falls back to `0` for a missing key, so **every keyword and every search term reads `inst=0` and `CR=0%`, unconditionally** — the `report` command cannot print a non-zero install for any row, ever. Verified against the raw API payload this run.

Why this matters, in the guard's own rules:

- **"NEVER negate a term that produced an install"** — this safety can never fire. The guard sees no installs.
- **"Proven waste: $3.00+ spent on that single term with 0 installs"** — fires on *winners*. Concretely, in campaign 2144852803 right now:

| keyword | match | taps | **real installs** | spend | **real install rate** | **real CPI** | what the guard sees | verdict under the $3 rule |
|---|---|---|---|---|---|---|---|---|
| `vision board` | EXACT | 2 | **1** | **$3.2607** | **50%** | **$3.26** | 0 inst, 0% CR | **would be negated** |
| `vision board app` | EXACT | 2 | **2** | $2.9943 | **100%** | **$1.50** | 0 inst, 0% CR | 1 cent from being negated |

`vision board app` is the best keyword in the Manifest account — 100% install rate at $1.50 CPI — and it sits $0.0057 below the threshold that would have killed it.

- **Step-5 recommendations are also broken**: "pause under 40% CR" would match every keyword and "raise at 60%+ CR" would match none.

The account converts normally, so this is purely a read bug, not an attribution problem — org-wide 2026-08-01..2026-11-06: **1,568 taps → 920 installs (58.7%)**.
