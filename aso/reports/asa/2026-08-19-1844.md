## The finding — the guard has been reading a field Apple stopped returning

`aso/asa_guard.py` reads `installs` from the reporting API. Apple's v5 grand/row totals do not
contain an `installs` key. The helper `_m()` treats a missing key as `0`, so **every report this
guard has written has silently claimed zero installs**. The real field names are `totalInstalls`
(and `tapInstalls` / `totalNewDownloads`).

Raw grand totals for campaign 2144421268, verbatim from the API this run:

```
"taps": 23,  "localSpend": 38.1376,
"tapInstalls": 4,        "totalInstalls": 4,       "totalNewDownloads": 4,
"tapInstallRate": 0.1739,"totalInstallRate": 0.1739,
"tapInstallCPI": 9.5344, "totalAvgCPI": 9.5344
```

There is no `installs` key at all. Same on every other campaign in the org.

### What this reverses

| Claim carried in past reports | Actual |
|---|---|
| 0 installs account-lifetime | **4 installs** on the Manifest campaign |
| CR = 0% | **CR = 17.4%** |
| CPI = n/a | **CPI = $9.53** |
| Rec: negate `journal` at restart | **`journal` produced 1 install — negating it was the wrong call** |
| Rec: `gratitude journal` is the first keyword to cut, 0-for-9 | **It is the best keyword: 3 installs, CR 33%, CPI $5.15** |

The `journal` line matters most. The standing recommendation across the last several reports was
`add-negatives "journal"` at restart. The brief's own hard rule is *never negate a term that produced
an install*. Executing that recommendation would have permanently blocked a converting query. It was
never executed, so nothing is lost — but it was one manual run away.
